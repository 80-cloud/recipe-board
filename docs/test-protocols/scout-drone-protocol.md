# Scout + Drone Protocol — 縦貫通単位の必須事前検証

> CRUD 実装で各「縦貫通の 1 機能」を着手する **前後** に必ず実施する 2 段プロトコル。
> 平常系のみの検証で見落とす重大発見を、構造的に炙り出すための仕組み。
>
> 「動いた」を「動作確認完了」と誤判定する習慣を防ぐ規律。

---

## 戦略の背景

S-01 実装の際、先回り 15 件のリスク予測に対して 3 件の "奇襲"（Step position バリデーション / `skip_forgery_protection` 不在 / SSR EmptyState フラッシュ）が発生した。

事後分析の結果、**「フレームワーク内部仕様の事前確認不足」** と **「平常系のみの動作確認」** が共通の真因と判明。これを構造的に防ぐため、**斥候（前方偵察）** と **ドローン（adversarial 投下）** を習慣化する。

---

## Phase 1: 斥候（Scout）— 着手前の前方偵察

### 目的

これから着手する画面の "敵情" を **コードを書かずに** 把握する。

### 必須項目

#### A. 設計書の深掘り読み
- [ ] 対象画面の「連携 API」セクションを精読（メソッド・パス・ペイロード）
- [ ] 「動作」セクションの遷移仕様を全パターン抽出
- [ ] 「バリデーション」セクションのクライアント側 / サーバー側両方を確認

#### B. 既存実装からの再利用ポイント特定
- [ ] 直前の縦貫通単位（S-01 等）で **どの基盤パターンが再利用可能か** を列挙
- [ ] 不足している基盤（serializer / Strong Params 等）を特定

#### C. フレームワーク仕様の確認（過去の奇襲対策）
- [ ] 関連モデルの **全バリデーション** を読む（過去事故: Step `position > 0`）
- [ ] 継承元クラスの仕様を確認（過去事故: `ApplicationController < ActionController::API` と `skip_forgery_protection` 不在）
- [ ] 使う API（`accepts_nested_attributes_for` / `useFetch` / `navigateTo` 等）の **「自分が知らない挙動」** がないかドキュメント参照
- [ ] SSR / CSR / hydration の境界に関わる挙動（過去事故: SSR EmptyState フラッシュ）

#### D. 過去事故ライブラリ突合
- [ ] `task-board/docs/incidents/cases/` を **症状 / 兆候 / 真因** の 3 段階で照合
- [ ] `_templates/incident-library/` も同様に照合
- [ ] 同型リスクが本機能に潜んでいないか確認

### 出力

**敵情リスト** を Issue / PR 本文に記載：

| 論点 | 難易度 | 対処方針 |
|---|---|---|
| 例: ネスト attributes 更新 | 高 | `accepts_nested_attributes_for(allow_destroy: true)` の挙動確認 |

## Phase 2: ドローン（Drone）— 既存実装への adversarial 投下

### 目的

**「平常系で動いた」を「動作保証」と誤判定しない**。意図的に異常を投げ込み、現実装の盲点を炙り出す。

### 標準ペイロード集

#### 🔴 必須（毎回投下）

| # | ペイロード | 目的 / 露出する可能性のある問題 |
|---|---|---|
| D-01 | **境界長文字列**（最大長ぎりぎり / 超過 / 空 / 1 文字）| バリデーション動作・UI レイアウト崩れ |
| D-02 | **XSS payload**（`<script>alert(1)</script>` / `<img onerror=>` ）| 自動エスケープが効くか |
| D-03 | **大量データ**（100 件以上）| pagination 不在 / N+1 / レンダリング性能 |

#### 🟡 推奨（時間が許せば）

| # | ペイロード | 目的 |
|---|---|---|
| D-04 | **異常 HTTP ステータス**（500 / 404 / 502）| ErrorState ハンドリング |
| D-05 | **遅延レスポンス**（5 秒スリープ）| Skeleton 実機表示 |
| D-06 | **壊れた JSON / 空配列** | パースエラー経路・EmptyState |
| D-07 | **絵文字 / マルチバイト / 改行 / NULL**| 文字コード・整形処理 |

#### 🟢 任意（特定機能で）

| # | ペイロード | 目的 |
|---|---|---|
| D-08 | **CORS 偽装**（許可外 Origin から）| CORS 防御の実機検証 |
| D-09 | **同時アクセス**（並列 fetch）| race condition / cache 衝突 |
| D-10 | **Mass Assignment payload**（POST/PATCH 時のみ）| Strong Params 漏れ検出 |

### 投下フロー

```
1. ペイロード投下
2. システム挙動の観察（ログ / レスポンス / 画面）
3. 想定どおり防御 → ✅ 記録
4. 想定外の挙動 → 🔴 即停止 → 真因分析（5 Whys）→ 修正 → 再投下
5. 投下後の必須クリーンアップ（テストデータ削除 / 通常状態に復元）
```

### 出力

**ドローン投下記録** を PR 本文に記載：

| ドローン | 結果 | 真因 / 評価 |
|---|---|---|
| 例: D-01 超長タイトル | ✅ 200文字でバリデーション弾き / 100文字は描画 | length: { maximum: 100 } が機能 |

## Phase 3: 結果の標準化

### 重大発見があった場合

`critical-finding-protocol.md` の Phase 4（標準化）を完遂する：
- [ ] `_templates/incident-library/` に事故記録
- [ ] `_templates/lessons-learned/INDEX.md` に教訓抽出
- [ ] 必要なら `scripts/preflight-check.sh` に検出ルール追加
- [ ] 本プロトコルのドローンペイロード集に新規 D-XX を追加

### 平常系のみだった場合

- [ ] 防御層が機能した証拠を記録（次回同型ペイロードで再確認可能にする）
- [ ] 後続の縦貫通単位でも継続適用

## 形骸化防止メカニズム

### 実施記録テーブル（毎縦貫通単位で必ず追記）

| PR | 機能 | 斥候実施 | ドローン実施 | 重大発見 | 適用日 |
|---|---|---|---|---|---|
| #41 / #42 | S-01 レシピ一覧 | ✅ 15件先回り | ✅ D-01/D-02/D-03 | 0 件（軽微 1 件: pagination 不在）| 2026-05-08 |

### B 振り返り（5 アプリ毎）の監査項目

`_templates/review-schedule.md` セクション B に追加：
- [ ] 直近 5 縦貫通で斥候+ドローンを **全件実施した割合**
- [ ] 未実施があった理由（時間不足 / 該当なし / 忘れ）
- [ ] 「該当なし」と書いた縦貫通の妥当性確認
- [ ] ドローンペイロード集の進化（新規 D-XX 追加件数）

→ 5 アプリ連続で「未実施・忘れ」が出たらプロトコルの **形骸化兆候**。`anti-formality-mechanism.md` の原則に従い見直す。

### 「使わない理由」の記録

該当なしで斥候+ドローンを省略した場合、PR 本文に **理由を明記**：
- 該当する API / UI 表示がない（純粋な内部リファクタ等）
- 既存の縦貫通でカバー済み
- 一時的な実験ブランチで提出物に含めない

→ 「忘れ」「面倒」は記録対象外（=形骸化警報）
