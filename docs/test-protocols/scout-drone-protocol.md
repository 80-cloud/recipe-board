# Scout + Drone Protocol v2 — 縦貫通単位の事前偵察

> **横展開原本との関係（修練城整備 #8 で明示・2026-05-10）:**
> - 横展開原本: [`_templates/test-protocols/scout-drone-protocol.md`](../../../_templates/test-protocols/scout-drone-protocol.md)
> - 本ファイル: recipe-board の **project-specific 版**（最も活発に更新中）
> - **同期方針**: recipe-board で改訂後、`_templates` 側へ手動反映（自動化は将来課題）
> - **新規プロジェクトの初期化時**: `_templates` 側を base として継承

> **概念モデル（5 行）**
> - 本体 = 実装中の機能（護るべき対象）
> - 多層防御 = **盾**（外部脅威から本体を護る・[CLAUDE.md セクション 12](../../CLAUDE.md) 参照）
> - 斥候 = 偵察員（本体着手前に前方の罠を確認する役）
> - ドローン = **使い捨ての囮**（斥候が運用してトラップを起動させる犠牲駒・記録のみ残しコードは残さない）
> - 斥候+ドローン = **矛**（盾と役割直交の攻撃的偵察手段）

## なぜ必要か（v1 からの本質的修正）

S-01 (PR #42) 実装の経験から、平常系のみの検証で **3 件の "奇襲"** が発生した。事後分析の結果、「フレームワーク内部仕様の事前確認不足」が共通の真因と判明。

v1（PR #44）はこの問題に応えようとしたが、**ドローンを "実装後の adversarial test" として配置** していたため、本来の「本体が無傷で済む偵察」の意図とずれていた。v2 はこれを修正する：

| 観点 | v1（誤）| v2（正）|
|---|---|---|
| ドローンの時期 | 実装後 | **実装前** |
| ドローンの寿命 | 結果記録として残す | **使い捨て**（観察のみ残す）|
| 攻撃対象 | 自分が書いた新コード | **本体が依存する既存環境・基盤・FW 仕様** |
| 役割 | 同列の検証手段 | 盾と直交する **矛** |

## 適用スコープ判定（最初に必ず通す）

形骸化防止のため、**全機能で必須にしない**。以下のマトリクスで適用 / 省略を判定する。

### 適用するべき（🟢）

- 既存基盤に深く依存する縦貫通（DB ↔ API ↔ UI が直接連携）
- 過去事故ライブラリに同型のリスクが既知
- 新規の FW 機能を初めて使う実装（serializer / 認証 / ネスト attributes 等）

### 省略可（🟡）

- 純粋な内部リファクタ・スタイル変更
- ドキュメント・コメントのみの変更
- 1 ファイル数行の単純な fix
- 既存パターンの単純な追加（例: 同型の新画面で再利用のみ）

### 即時実装すべき（🔴）

- 提出締切まで残り 1 日未満（機会費用過大）
- セキュリティ脆弱性の即時 patch

→ PR 本文に **「適用 / 省略 + 理由」を 1 行で記載**。「忘れ」「面倒」は形骸化警報。

### v3.2 強化ルール: 🟡 でも Phase 1-D（過去事故突合）だけは必須

🟡（省略可）と判断した場合でも、**Phase 1-D の過去事故ライブラリ突合だけは必ず実施**する。理由：

- 当初 🟡 と判断した B-5-δ で、過去事故突合により 3 件の関連事故を発見し 🟢 に格上げした実例
- 過去事故突合は時間コストが小さい（5〜10 分）一方、見逃した場合の損失は大きい（同型事故の再発）
- 「🟡 から 🟢 への格上げ」を **構造的に許容**する仕組み

→ 🟡 で省略を決断する場合も「過去事故突合の結果、同型リスクなしと確認した」を PR 本文に記載する。

### v3.2 強化ルール: git mechanics 層は階層に関わらず適用必須

「Git mechanics 層ペイロード」（D-GIT-01〜04）は、**🟢🟡🔴 の判定に関わらず**、すべての PR で適用される。これは過去 3 回の再発を踏まえた強制ルールである。

## 達成 Level ヒエラルキー（v3.3 で導入）

> v3.2 までは「罠を見つけて回避する」が主眼だったが、これは **遠回りを毎回繰り返す = 時限爆弾化** の問題を抱えていた。
> v3.3 では各 Finding に対して達成すべき **整備 Level** を明示し、L4（道路自体の改修）を最優先で目指す。

### Level 定義

| Level | 名称 | 内容 | 永続性 | 例 |
|---|---|---|---|---|
| **L1** | 認識 | incident-library に記録するだけ | **0%**（読まなければ無意味）| 「t2.micro は東京で課金される」と書いただけ |
| **L2** | 回避 | 今回だけ別ルート / 注意して通る | **0%**（次回も同じ罠が待っている）| 「t3.micro を選んだ」だけで variable に default なし |
| **L3** | 解体 | この個別ケースから罠を取り除く | **50%**（同じ場所には現れないが類似罠は残る）| 既存の課金リソースを delete |
| **L4** | 整備 | 道路自体を改修、罠の存在可能性を消す | **100%**（構造的に再発不能）| `validation` block で選択不可化 / Hook で機械的検知 |

### 判定原則

1. **L4 を最優先で目指す**。L4 が実現可能なら必ず L4 を選ぶ
2. **外部制約でも L4 は可能なことが多い**：制約自体は変えられなくても、コード / 仕組みでその制約に触れられない構造を作れる
3. **L1 / L2 留まりは時限爆弾**：その Finding は「忘れたら事故になる」状態
4. **L3（解体）と L4（整備）の違い**：解体は「今ここの罠」を消す、整備は「同型の罠が再発できない」構造を作る

### Level 判定実例（本プロジェクトの過去 Finding）

| Finding | 種類 | 達成 Level | 整備の中身 |
|---|---|---|---|
| F1: t2.micro 無料枠外（東京）| 外部制約 | **L4** | `variables.tf` の `validation` block で **選択不可化** |
| F2: 停止中 EIP 課金 | 既存資産 | **L3** | release-address で個別解体（L4 化案：Terraform lifecycle で auto-release）|
| F3: RDS 7 日自動再起動 | 外部仕様 | **🔴 L1**（時限爆弾）| 認識のみ。L4 化案：weekly auto-stop / 「不要時は destroy」運用 |
| F4: 750h account 単位 | 運用ルール | **L4** | D-EC2-COUNT Hook で apply 直前に running 数チェック |
| F5: AWS Budgets は通知のみ | 外部仕様 | **L3** | deletion_protection / prevent_destroy で別防御層 |
| cwd / branch state 同型 3 回再発 | プロセス | **L4** | D-GIT-01 Hook で機械的検知 |

→ **L4 を達成した項目は、達成後に再発していない**。経験的証拠。

### 形骸化防止策（v3.3 で本ヒエラルキー自体に組み込む）

| 機構 | 内容 |
|---|---|
| 達成 Level フィールド必須化 | 全 Finding に Level を明示。空欄禁止 |
| 🔴 残存件数の継続監視 | B 振り返り監査で「L1 / L2 のまま N 件」を集計 |
| Phase 5 の解体完了確認 | Phase 4 を経ずに完了宣言できない構造 |
| 形骸化警報 | L1 / L2 のまま 30 日経過で自動アラート（Phase D watchdog 連動）|

## 運用フロー（時系列）

```
[ 着手前 ]
  ⓪ 本体進行の中断判定（Phase 0・v3.5 で明示化）
       - 罠の予兆 / 奇襲 / 同型 finding 検知 → 即停止
       - 進行中なら一旦停止してから斥候へ
  ① 斥候: 設計書深掘り + 既存実装再利用ポイント特定
  ② 斥候: 過去事故ライブラリ突合（symptom/sign/cause の 3 段照合）
  ③ 斥候: フレームワーク内部仕様の実コード読み（モデル / 継承元 / 規約）
  ④ 斥候: 疑わしい "罠候補" を特定し、ドローンの飛行計画を立てる
  ⑤ ドローン投下: 既存環境・基盤に試し撃ち（必須 D-01〜D-03 + 該当する 🟡）
  ⑥ 観察: 起動したトラップを観察・記録（コードは残さず観察のみ残す）
  ⑦ 教訓化: 起動したトラップは incident-library に永続化（使い捨ての囮の学びは残す）

[ 着手 ]
  ⑧ 本体実装: 取得した教訓を実装計画に反映してから着手
       ※ 実装中に奇襲発生 → Phase 0 に戻る（即中断 → 斥候 → ドローン → 整備 → 再開）

[ 完了直前（v3.3 で必須化）]
  ⑨ 整備作業（Phase 4）: 各 Finding に対し L4（道路整備）を最優先で実装
                          L4 不可なら L3 / L2 / L1 と理由を明示
                          整備の二重目的（v3.5 で明文化）:
                            短期 = 今回の本体が安全に通れる
                            長期 = 次回同じルートで最短到達（罠が無い状態で無確認通行）
  ⑩ 整備完了確認（Phase 5）: 達成 Level の判定、🔴（L1/L2 留まり）残存ゼロを確認
                              残存があれば follow-up Issue で持ち越し管理

[ 完了後・別カテゴリ ]
  ⑪ Regression chaos test: 完成した本体への事後 adversarial 検証（別プロトコル扱い）
```

→ **罠を見たら本体を止める。斥候+ドローンは着手前または奇襲直後。整備の目的は今回の安全だけでなく次回の最短化。**

## Phase 0: 本体進行中断判定（v3.5 で導入）

### 動機

v3.4 までは「着手前」「着手」の暗黙ライフサイクルだった。罠の予兆や奇襲が出た時の **「即停止判定」** が明示されていなかったため、本体作業を止めずに L2 回避を続ける運用が生じた（2026-05-10 セッション D-DESTRUCT-REGEX self-bite 5 回再発の真因）。

v3.5 で **Phase 0「本体進行中断判定」** を新設し、罠検知 → 即停止 → 斥候 → 整備 → 再開のシーケンスを明示する。

### 判定マトリクス

| 検知タイミング | 種別 | 判定 |
|---|---|---|
| 着手前 scout | 罠の予兆 | Phase 1〜5 へ進む（既存フロー） |
| 着手前 scout | 過去事故同型 | Phase 1〜5 へ進む（既存フロー）|
| 着手中 / 実行中 | 奇襲（未知の挙動） | **即停止 → Phase 1（事中斥候）→ ドローン → 整備 → 再開** |
| 着手中 / 実行中 | 同型 finding 再発（2 回目以降）| **即停止 → 整備 L4 昇格を最優先**（[feedback_drone_first_default](#) 適用）|
| 着手中 / 実行中 | self-bite / フック誤発火 | **即停止 → 真因調査 → L4 整備提案** |

### 中断 vs 一時継続の判断軸

| 条件 | 行動 |
|---|---|
| 不可逆性高（destroy / 課金 / 機密漏洩リスク） | **即中断** |
| 同症状の N 回再発（N ≥ 3） | **即中断 + L4 昇格** |
| 時間制約明確（締切 1 日未満）+ user 同意 | 一時継続 + 整備候補として記録（L2 回避を意識的選択） |
| 影響範囲限定 + user 明示承認 | 一時継続可 |

### Phase 0 違反のシグナル

以下が観測されたら Phase 0 が機能していない:

- 罠検知後も本体作業を継続している（停止 step を経ずに次の作業へ）
- 同型罠の N 回再発を「既知パターン」として記録するだけで止めない
- 「とりあえず回避」を default にして調査をスキップ

### Phase 0 で停止した場合の責任

- 必ず Phase 1〜5 を最後まで通す（**整備をスキップして再開しない**）
- 整備完了後の本体再開は「次回同じルートで最短到達できる状態」を確認してから

## Phase 2: ドローン投下（既存環境への試し撃ち）

### 設計原則
- ドローンは **既存環境**（既存コード・既存ルート・既存設定）に対して飛ばす
- **本体（新コード）は書く前**
- ドローン用に書いたコードは **観察後に破棄**（残すのは観察結果と教訓のみ）
- 1 件のドローンは **15 分以内** に観察終了（分析麻痺防止）

### 必須ペイロード（🔴 5 件・2026-05-09 X-01/X-02 を踏まえて 2 件追加）

| # | ペイロード | 投下対象（既存環境）| 観察ポイント |
|---|---|---|---|
| **D-01** | 境界長文字列 | 既存モデルバリデーション | length 制限・絵文字・null |
| **D-02** | XSS payload | 既存 Vue コンポーネント / SSR | 自動エスケープが効いているか |
| **D-LZ** | **実ブラウザの CSR 遷移**（NuxtLink クリック / `<a>` でない経路）| 既存 hydration / Vue Router / DevTools 統合 | **「SSR curl 通過 ≠ ブラウザ hydration 通過」**（[X-01 同型](../../../_templates/incident-library/2026-05-09-nuxt-devtools-vue-router-hydration.md)）|
| **D-CACHE** | **mutation → 別画面遷移 → 期待値表示**（POST/PATCH/DELETE 後に他画面で結果を観察）| 既存 useFetch / SWR / Apollo 等のクライアントキャッシュ | mutation 後に古い値が残らないか（[X-02 同型](../../../_templates/incident-library/2026-05-09-usefetch-cache-invalidation-after-mutation.md)） |
| **D-03** | 大量データ | 既存一覧 API・既存 Nuxt SSR | pagination 不在 / N+1 / 描画性能 |

### 推奨ペイロード（🟡）

| # | ペイロード | 投下対象 | 観察ポイント |
|---|---|---|---|
| D-04 | 異常 HTTP ステータス | 既存 ErrorState | レスポンス body 形式・UX |
| D-05 | 遅延レスポンス | 既存 LoadingSkeleton | 表示タイミング |
| D-06 | 壊れた JSON / 空配列 | 既存 useFetch | パース失敗経路・EmptyState |
| D-07 | 絵文字 / マルチバイト / 改行 | 既存全層 | 文字コード・整形 |

### 任意ペイロード（🟢）

| # | ペイロード | 投下対象 | 観察ポイント |
|---|---|---|---|
| D-08 | CORS 偽装（許可外 Origin）| 既存 CORS 設定 | 防御の実機検証 |
| D-09 | 同時アクセス（並列 fetch）| 既存キャッシュ | race condition |
| D-10 | Mass Assignment payload | 既存 Strong Params | 漏れ検出 |

### Infra 層ペイロード（🟢🟡 v3.2 で正式追加）

infra（Terraform / AWS / IaC）系の縦貫通では、上記の app 層ペイロードがほぼ適用外になる。代わりに以下を投下する。すべて **read-only な AWS API** であり、課金・本体起動・新規リソース作成を伴わない。

#### 必須ペイロード（🔴・infra 系縦貫通で適用必須）

| # | ペイロード | 投下対象（既存環境）| 観察ポイント |
|---|---|---|---|
| **D-INFRA-01** | 認証アイデンティティ確認 | `aws sts get-caller-identity` | 想定 IAM user / account ID と一致 |
| **D-INFRA-02** | デフォルト VPC 確認 | `aws ec2 describe-vpcs --filters "Name=is-default,Values=true"` | data source が解決可能 |
| **D-INFRA-03** | free-tier EC2 タイプ確認 | `aws ec2 describe-instance-types --instance-types <type>` | **リージョン依存性チェック**（ap-northeast-1 で t2.micro は対象外）|
| **D-INFRA-04** | free-tier RDS engine version 確認 | `aws rds describe-orderable-db-instance-options` | 利用可能 engine_version の検証 |
| **D-INFRA-05** | 既存 EIP 監査 | `aws ec2 describe-addresses` | 孤立 EIP / stopped EC2 アタッチによる課金リスク（[2026-05-09-eip-stopped-ec2-charge](../../../_templates/incident-library/2026-05-09-eip-stopped-ec2-charge.md)） |

#### 推奨ペイロード（🟡）

| # | ペイロード | 投下対象 | 観察ポイント |
|---|---|---|---|
| D-INFRA-06 | 既存稼働 EC2 監査 | `aws ec2 describe-instances` | 想定外稼働の検出 |
| D-INFRA-07 | 既存 RDS 監査 | `aws rds describe-db-instances` | ストレージ無料枠の合算 |
| D-INFRA-08 | RDS ストレージ詳細 | `aws rds describe-db-instances --query '[].AllocatedStorage'` | 無料枠 20GB 上限の合算チェック |
| D-INFRA-09 | AWS Budgets 設定 | `aws budgets describe-budgets` | 検知レイヤーの有無確認 |

→ infra 系縦貫通では D-INFRA-01〜05（必須 5 件）を最低投下し、🟡 は文脈で判断する。

### Git mechanics 層ペイロード（v3.2 で新設）

cwd / branch state の管理ミスは本プロトコル運用中に **3 回再発**した（[2026-05-09-cwd-branch-state-3rd-recurrence](../../../_templates/incident-library/2026-05-09-cwd-branch-state-3rd-recurrence.md)）。app 層・infra 層に並ぶ第 3 のドローンカテゴリとして正式追加する。

#### 必須ペイロード（🔴・全 git / gh / aws コマンドで適用必須）

| # | ペイロード | 投下対象 | 観察ポイント |
|---|---|---|---|
| **D-GIT-01** | cwd / branch 直前確認 | `pwd && git branch --show-current` の手動出力 | **全 git / gh コマンドの直前に必ず実行**。期待 cwd / branch と不一致なら明示 cd で修正 |
| **D-GIT-02** | stacked PR 警告 | `gh pr view --json baseRefName` | base ブランチが merge `--delete-branch` で削除されないか事前確認。stacked の場合は base を main に切替えてからマージ |

#### 推奨ペイロード（🟡）

| # | ペイロード | 投下対象 | 観察ポイント |
|---|---|---|---|
| D-GIT-03 | 絶対パス git の活用 | `git -C <full-path> <command>` | cwd 非依存化。複数リポジトリ横断作業で特に有効 |
| D-GIT-04 | gh `--repo` 明示 | 全 `gh` コマンド | cwd 起点の repo 解決を回避。2 回目再発（2026-05-09-cross-repo-cwd-mistake-recurrence）の対策 |

→ git mechanics は **すべての階層**（app / infra / docs）で適用必須。本ドローンは省略不可。

```
1. 飛行計画（どの罠を狙うか・観察ポイントは何か）を Issue / PR に明記

3. 観察記録（ログ / レスポンス / 画面状態）
4. ドローンコード破棄（コミットしない）
5. トラップ起動 → incident-library に永続化
   トラップ起動せず → 防御層が機能した証拠として観察記録のみ残す
6. 必須クリーンアップ（テストデータ削除 / DB 状態復元）
```

## Phase 4: 整備作業（v3.3 で必須化）

> 本フェーズは v3.3 で追加。「罠を見つけて回避する」止まりだった v3.2 までの構造的弱点を塞ぐ。

### 設計原則

- **各 Finding に対し L4（整備）を最優先で目指す**
- L4 が不可能な場合のみ L3 / L2 / L1 にフォールバック
- フォールバック時は **理由を明示**（「面倒」「忙しい」は形骸化警報）
- 「外部制約だから整備不可」は誤解。**外部制約でも L4 は実現可能なケースが多い**（例: validation block, Hook）

### 整備の実装パターン

| Finding 種類 | L4 整備の典型パターン |
|---|---|
| 外部制約（API / 規約 / 仕様）| `validation` block / 型システム / Linter ルールで触れられない構造を作る |
| 既存資産（課金中リソース 等）| 自動化スクリプト + Terraform lifecycle で再発生防止 |
| 運用ルール（注意事項）| Hook / pre-commit / CI で機械的検知 |
| プロセス（人間記憶依存）| Hook / scheduled task / watchdog で自動化 |

### 整備実施チェックリスト

各 Finding ごとに以下を実施：

- [ ] L4 整備案を最低 1 つ検討した
- [ ] L4 が選択された場合、その実装が完了している
- [ ] L4 が不可能と判断した場合、その**理由が具体的に書ける**
- [ ] L3 へのフォールバックなら、解体実装が完了している
- [ ] L2 / L1 留まりは **follow-up Issue として起票**されている

### Finding 表（PR 本文の必須要素）

PR 本文には以下のフォーマットの Finding 表を必ず記載：

```markdown
| Finding | 種類 | 達成 Level | 整備の中身 / 残置理由 |
|---|---|---|---|
| F-XX | （外部制約 / 既存資産 / 運用ルール / プロセス）| L1〜L4 | （具体内容）|
```

→ **空欄 / 「TBD」/ 「あとで」は禁止**。記述できないなら Phase 4 未完。

## Phase 5: 整備完了確認（v3.3 で必須化）

> Phase 4 の作業結果を**機械的に検証**する。完了宣言の前にゲートとして必須。

### 完了条件

| 確認項目 | 達成基準 |
|---|---|
| 全 Finding に達成 Level が記載されている | ✅ 空欄ゼロ |
| L4 が達成可能な Finding でフォールバックしていない | ✅ L4 実装完了 |
| 🔴（L1 / L2 留まり）の Finding に follow-up Issue がある | ✅ Issue 番号付き |
| 「形骸化警報」（理由が薄い L2 留まり 等）がない | ✅ 理由が具体的 |

### 達成率メトリクス

```
解体率 = (L3 + L4) / 全 Finding 数
時限爆弾率 = (L1 + L2) / 全 Finding 数
L4 達成率 = L4 / 全 Finding 数
```

→ B 振り返り監査（5 アプリ毎）でメトリクス推移を集計。

### 形骸化警報のシグナル

以下を検知したら**警報**：

- 🚨 「達成 Level = L1（記録のみ）」が 3 件以上溜まった
- 🚨 同型 Finding が 2 回以上発生（同じ罠が繰り返されている）
- 🚨 「達成 Level: L4」と書かれているが実装が不在
- 🚨 follow-up Issue が 30 日以上 open のまま

これらは **Phase D watchdog（v3.2 で別途設計）と連動**して自動検知することを目標とする。

### Phase 5 を経ずに「完了」と宣言した場合

→ **形骸化原則違反**。incident-library に「Phase 5 スキップ事故」として記録する。

## Phase 6: 自己監視（Quis custodiet）— 衛兵八重原則（v3.4 で導入）

### 動機

Phase 1-5 は外敵（罠 / 過去事故）に対しては機能するが、**防御層自体の改ざん・形骸化・自爆**には穴があった。`2026-05-09-insider-threat-meta-finding` で識別した 6 シナリオ（A-F）のうち B のみ対処済で、A/C/D/E/F が未対処だった。

2026-05-10 セッションで以下が **実証された予兆** として観測された：
- `D-EC2-COUNT` の `terraform -chdir=...` bypass（hook が想定通り動かない・シナリオ A 前兆）
- `D-DESTRUCT-REGEX` 同類 bug（修練城最重要層の同じ穴・「衛兵を見張る衛兵」必要性の決定的証拠）
- Hook self-bite の false positive 再発（reflexive approve への助走・シナリオ F 前兆）

→ Phase 6 で **「衛兵を見張る衛兵」** を protocol に正式組み込み。

### 衛兵八重とは

防御層自体を別の層が監視する **多重自己監視構造**。8 という数字は象徴的（実装は階層化されたチェック群）。

| 階層 | 役割 | 既存実装 |
|---|---|---|
| 1: **本防御** | 既存修練城（hook / deny / branch protection / pre-commit / gitleaks / etc.）| 多数 |
| 2: **編集ガード** | critical file の編集に ask permission（`Edit(/Users/macmini/.claude/settings.json)` 等 16 ルール）| `permissions.ask` |
| 3: **改訂強制** | 改訂時は必ず Issue → PR → review。直接編集禁止 | CLAUDE.md セクション 11 |
| 4: **自己テスト** | hook 追加・改訂時に **16+ ケースのユニットテスト必須** | `/tmp/test-d-*-regex.py` テンプレ |
| 5: **発火ログ** | 各 hook が `/tmp/d-*-fired.log` に記録 | 既存 hook で実装済 |
| 6: **形骸化検知** | watchdog で「使われてない防御」「古い incident」を月次検出 | `incident-watchdog.yml` 拡張対象 |
| 7: **メモリ監査** | feedback memory の週次レビュー（汚染・古さ・矛盾） | v3.4 新設手順 |
| 8: **人間 audit** | B 振り返り（5 アプリ毎）で全層の状態を人手確認 | `_templates/review-schedule.md` 拡張対象 |

### 6 insider シナリオへの v3.4 対処マトリクス

| シナリオ | v3.3 までの状態 | v3.4 対処 | 対応する衛兵階層 |
|---|---|---|---|
| **A**: Hook 自体の改ざん | L1 | hook 自己テスト + ask permission + 発火ログ集計 | 階層 2 / 4 / 5 |
| **B**: acceptEdits の盲点 | L4 ✅ | （既対処）| 階層 2 |
| **C**: incident-library 形骸化 | L2 | watchdog 拡張 + 月次「使ってない事故」audit | 階層 6 / 8 |
| **D**: 効率化口実の防御剥がし | L2 | feedback memory + ask + class 抽象化ルール | 階層 2 / 7 |
| **E**: メモリ汚染 | L1 | memory 編集 ask（既存）+ 週次レビュー手順（新設）| 階層 2 / 7 |
| **F**: reflexive approve | L1 | hook ノイズ ratio 検知 + 自己テストで false positive 削減 | 階層 4 / 5 / 6 |

### Phase 6 必須サブフェーズ

#### 6-A: Hook 自己テスト機構（追加・改訂時）

新規 PreToolUse hook を追加するとき、または既存 hook の regex を変更するときは **必ず**：

1. **16+ ケース**のユニットテスト（true positive / true negative / false positive / false negative の 4 象限すべて）
2. テスト script は `/tmp/test-d-<hookname>-regex.py` 形式
3. テスト pass を **PR 本文に貼る**（PR review で見える形に）
4. **標準 regex pattern library**（v3.4 で確立）を再利用：
   - `terraform[[:space:]]([^|;&]*[[:space:]])?<verb>([^a-zA-Z0-9_-]|$)` で `terraform [<flags>] <verb>` を網羅
   - `[^|;&]*` で `|;&` を含まない（コマンド境界を超えない）
   - `[^a-zA-Z0-9_-]` で word boundary 相当（`apply` と `applying` を区別）

#### 6-B: 形骸化のメタ警報

月次（または各 B 振り返り時）に以下を確認：

| シグナル | 検出方法 | 対応 |
|---|---|---|
| 0 fire の hook | `/tmp/d-*-fired.log` 行数 = 0 | 「使われてない防御」候補・廃止 or 規律化検討 |
| ノイズ ratio 閾値超過 | `(false fire 件数) / (全 fire 件数)` > 0.5 | reflexive approve リスク・regex 精度向上 |
| 古い incident 不参照 | git log でファイルが N ヶ月触られていない | 形骸化候補・カテゴリ整理 or 削除検討 |
| memory 矛盾検出 | 週次レビューで feedback 間の矛盾検知 | 統合 or 廃止 |

#### 6-C: 改訂時の self-bite 対策（2026-05-10 実証パターン）

修練城自身を強化する作業（hook 追加 / settings.json 編集 / scout-drone 改訂）では：

1. **コマンド本文に禁止語リテラルが入らない設計**（`feedback_chaos_test_self_falsepositive`）
2. Issue / PR / commit body はファイル経由で渡す（`gh ... --body-file`、`git commit -F`）
3. 修練城自身の改訂は class 抽象化（個別 fix ではなくパターン全体への対策）

#### 6-D: 「衛兵を見張る衛兵」原則の運用

無限後退を避けるため、以下の現実解：

- **ピラミッド構造**: 各層は下位層を監視。最上位は **人間（B 振り返り）**
- **AI を信用しすぎない**: AI は内通者になり得る（過去事故 `2026-05-07-ai-overrode-learning-context`）。critical file は ask permission で人間判断を必ず挟む
- **形骸化への耐性**: 形骸化検知自体が形骸化しないため、watchdog の watchdog（メタ警報）を組み込む

### Phase 6 形骸化警報

以下が観測されたら Phase 6 自体が機能していない：

- 6 ヶ月以上 hook の自己テストが追加されていない
- `permissions.ask` の critical file リストが直近 1 年更新されていない
- B 振り返りで Phase 6 監査項目をスキップ
- 「衛兵八重」の階層に空白がある（特定階層が常に空）

### Phase 6 適用判定

| 判定 | 適用範囲 |
|---|---|
| 🟢 必須 | hook 追加・改訂、settings.json 編集、scout-drone 改訂、CLAUDE.md セクション 12 改訂 |
| 🟡 推奨 | incident-library 追加・編集、memory feedback 追加 |
| ⚪ 不要 | アプリコード（infra 以外）の通常変更 |

## 修練城の標準シーケンスと drone = 学習装置 view（v3.5 で確立）

### 修練城の標準シーケンス（5 段ループ）

```
本体進行中
  ↓ 罠の予兆 / 奇襲 / 同型 finding 検知
[Phase 0] 本体進行を中断  ← 最初のアクション（暗黙ではなく明示）
  ↓
[Phase 1] 斥候で調査  （三現主義 / 過去事故突合 / 真因深掘り）
  ↓
[Phase 2] ドローンで罠を発見  （静的観察ペイロード投下）
  ↓
[Phase 4] 整備  （二重目的:
            ① 短期: 今回の本体が安全に通れる
            ② 長期: 次回同じルートで最短到達するため = L4 の数学的帰結）
  ↓
本体が進行を再開（安全 + 次回以降は無確認で通れる状態）
```

### 整備の二重目的

| 目的 | 内容 | 達成 Level |
|---|---|---|
| 短期 | 今回の本体が罠を踏まずに通れる状態を作る | L3 解体（最低限） |
| 長期 | 次回同じルートで最短到達できる状態 = 罠が無い構造 | **L4 整備（推奨）** |

→ L4 整備が完了すれば「次回は無確認通行可能」 = 修練城のスループット向上。

### drone = 学習装置 view

drone 投下は単なる trap detection ではなく、**修練城の認知能力への投資**。

| 観点 | 浅い view | 深い view |
|---|---|---|
| 回避の意味 | 同型罠を毎回避ける | **学習機会の喪失** |
| drone の意味 | 罠を見つける手段 | **学習装置**（罠構造の蓄積機構） |
| L4 整備 | 構造的再発不能化 | **学習成果の物理化** |
| 修練城 | ルールベース防御 | **生成型知識基盤**（蓄積で対処速度が指数的向上） |

### drone 投下を続けるサイクル（蓄積による加速）

```
drone 投下 → 罠発見 → incident-library 永続化
  ↓
過去事故突合の精度向上（Phase 1-D の効率化）
  ↓
新規プロジェクトで「罠の予兆」段階で検知可能化
  ↓
本体が中断する頻度が減る（事前防御で済む）
  ↓
修練城のスループットが向上
  ↓
余裕で更に深い drone 調査が可能
  ↓ (ループ)
```

→ drone 投下を続けるほど、修練城は **自己進化** する。

### 回避を続けるサイクル（停滞）

```
回避 → 罠は残る → 同型罠で再度遭遇
  ↓
蓄積ゼロ・対処コスト一定
  ↓
規模拡大時に破綻（同型罠が N 件 → N×回避コスト）
```

→ 回避を続けても修練城は **同じサイズで停滞**。

### 回避を default にしない原則

罠 / self-bite / 同型問題が発生したら **default は drone 調査 + 修正案提示**。L2 回避を選ぶのは下記のいずれかのみ:

1. 時間制約: 締切 1 日未満等の明確な時間制約 + user が同意
2. 緊急時: 修正の余裕がない（事故対応中等）
3. user 明示承認: 「今は回避でいい」と user が言う

それ以外は drone を投下して L4 整備案を提示し、user の判断を仰ぐ（[feedback_drone_first_default](#) と整合）。

## 罠の予兆 vs 奇襲の 2 系統（v3.5 で整理）

両者とも標準シーケンス（Phase 0 中断 → 斥候 → ドローン → 整備 → 再開）に入るが、**進入タイミングが異なる**。

### 比較表

| 観点 | 罠の予兆 | 奇襲 |
|---|---|---|
| 検知タイミング | scout phase（着手前） | 本体実行中・突如 |
| 予測可能性 | 高（過去事故突合 / 設計書精読） | 低（未知の挙動） |
| Phase 0 中断 | 事前 | 事中（即座） |
| 標準シーケンス | 同じ | 同じ |
| 整備後の効果 | 同型罠の予兆検知能力向上 | **未知の奇襲が罠の予兆に格上げ**（最大の学習成果） |

### 奇襲の戦略的価値

奇襲は **「これまで予兆として認識できなかったクラスの罠が顕在化する」** 瞬間。修練城の認知盲点が露わになる = **最大の学習機会**。

奇襲を回避すると、その奇襲は将来も奇襲のまま再発する。drone で調査して整備すれば、次回からは罠の予兆として検知可能になる。

### 過去の奇襲事例と整備（実績）

| 奇襲 | 整備内容 |
|---|---|
| `2026-05-09-nuxt-devtools-vue-router-hydration` (X-01 光学迷彩) | scout-drone v2.1 で **D-LZ ペイロード**新設 |
| `2026-05-09-usefetch-cache-invalidation-after-mutation` (X-02) | v2.1 で **D-CACHE ペイロード**新設 |
| `2026-05-09-cwd-branch-state-3rd-recurrence` | feedback_cd_prefix_mandatory（class 抽象化） |
| `2026-05-10` D-DESTRUCT-REGEX self-bite (5 回再発) | L4 fix（gh/git commit guard 節）+ feedback_drone_first_default |

→ いずれも奇襲を整備で罠の予兆に格上げした実例。

## デメリットと既知の限界

このプロトコルは万能ではない。以下を認識した上で運用する：

| デメリット | 緩和策 |
|---|---|
| **時間オーバーヘッド** | スコープ判定マトリクスで省略可 |
| **使い捨て性によるレバレッジ不足** | トラップ起動時 incident-library 永続化 必須化 |
| **斥候の知識限界が天井** | サブフェーズ B（既存読み）と D（過去事故突合）でカバー |
| **未知の罠は撃ち抜けない** | サブフェーズ C（FW ソース実読）で補完 |
| **「やった気」の形骸化** | B 振り返り監査の予測精度メトリクスで検出 |
| **bikeshedding / 分析麻痺** | 1 ドローン 15 分・必須は 3 件のみ |
| **チェックリスト疲れ** | PR テンプレを "適用 / 省略 + 理由" の簡素形に |
| **学習 MVP に過剰** | 適用しない条件を明示 |

## 形骸化防止メカニズム（拡張版）

### 実施記録テーブル

| PR | 機能 | 適用判定 | 斥候 | ドローン | 起動した罠 | 予測精度（予測/奇襲）| 適用日 |
|---|---|---|---|---|---|---|---|
| #41/#42 | S-01 一覧 | 🟢 適用 | ✅ | ⚠️ 事後実施（v1 の誤運用）| pagination 不在のみ | 15 / 3 | 2026-05-08 |

### B 振り返り（5 アプリ毎）の監査項目

`_templates/review-schedule.md` セクション B に組み込み（dev-templates 別 PR で更新）：

- [ ] 直近 5 縦貫通で適用判定の妥当性確認（適用すべきだったのに省略していないか）
- [ ] **予測精度メトリクス**: 斥候が予測できた件数 vs 実際に発生した奇襲件数
- [ ] **ドローン命中率**: 投下したドローン数 vs 起動したトラップ数
- [ ] **使い捨て規律**: ドローンコードが誤ってコミットされていないか（`git log` で grep）
- [ ] 「該当なし / 省略」省略の理由分布（妥当 / 形骸化警報）

## 禁止用語と運用ルール（v3.1: 2026-05-09 #59 で追加）

### 経緯

Phase 4 Pre Phase で R-D-XX 投下時に「**retrospective drone**」という曖昧な言葉で scout-drone と regression chaos test を**混同**し、結果として **本体（Rails dev / Nuxt dev）を起動して挙動を観察**してしまった。データ破壊や副作用は無かったが、「本体は護るべき対象」という戦略原則の違反。

### 禁止用語

以下の曖昧な用語は本プロトコル運用で**使用禁止**：

| 禁止用語 | 理由 | 推奨 |
|---|---|---|
| "retrospective drone" | scout-drone と regression chaos test を混同 | **"regression chaos test"**（本体起動）または **"斥候（静的観察のみ）"** |
| "事後ドローン" | 同上 | 同上 |
| "drone 検証" 文脈での本体起動 | 「ドローンは既存環境のみ対象」原則違反 | "regression chaos test として実施" と明示 |

### 本体起動を伴う検証の事前申告ルール（必須）

以下の操作は **「本体起動を伴う検証 = regression chaos test」** に該当し、**実施前に明示的な申告と承認**が必要：

- `bin/rails s` / `bin/rails runner` で**アプリ全体を boot** する操作
- `npm run dev` / `npm run preview` 後の起動
- `curl` で**本体エンドポイント**を叩く操作
- 本体プロセスを起動する任意のコマンド

実施前に Issue / PR / 会話で以下を明示：

1. **「これは regression chaos test です」** と宣言
2. **検証目的・観察ポイント・想定される副作用**を記載
3. **承認を待つ**

→ 「ドローン」と称して本体起動を伴う操作を行うことは**禁止**。
