## 2026-05-08: GitHub アカウント名の誤認事故（プロジェクト初期セットアップ時）

### 何をしたか

プロジェクト初期セットアップ中、GitHub リポジトリの URL を CLAUDE.md / README.md に記載する際、
ローカルの git config の `user.name`（hideharu-AI）を GitHub アカウント名と誤認した。

### つまずいた点

- CLAUDE.md と README.md の合計 5 箇所に `hideharu-AI/recipe-board` という URL を記載してしまった
- 実際の GitHub アカウント名は `80-cloud`（`gh api user --jq '.login'` で確認）
- 誤った URL のままコミット（`9b08e0f chore: プロジェクト初期化`）してから誤りに気づいた

### 発覚プロセス

push 直前に `gh auth status` で認証状態を確認した際、`80-cloud` で認証されていた。
Claude が「認証アカウントと記載した URL の owner が違う」ことに気づいて、ユーザーに報告。
`gh api user` で実アカウント名を確認して事実が確定した。

→ **「実行こそ真実」が機能した好例**。会話・推測ではなく、実コマンドで真偽を確定させた。

### 5 Whys（なぜなぜ分析）

| 段階 | 内容 |
|---|---|
| なぜ 1 | Claude が `hideharu-AI` を GitHub アカウント名と仮定した |
| なぜ 2 | ローカル git の `user.name` を確認したが、それが GitHub と同じだと思い込んだ |
| なぜ 3 | GitHub 認証情報を最初に確認するステップを省略した |
| なぜ 4 | 「個人アカウント vs 組織」の会話の流れで、検証より推測を優先した |
| なぜ 5 | 新規プロジェクト開始時の事前検証ルール（Pre-flight Check）が未確立だった |

→ **真因**：新規プロジェクト開始時の Pre-flight Check 体系の不在。

### 修正内容

- 修正方法は「amend」ではなく「追加コミット」を選択（履歴を残すため）
- 追加コミット: `53e32ed docs: GitHub リポジトリURLを 80-cloud/recipe-board に修正`
- 修正範囲: README.md (1箇所) / CLAUDE.md (4箇所) → 計 5 箇所

### 標準化（S = Standardize）— 4 層の再発防止策

| 層 | 対策 | 配置場所 | 状態 |
|---|---|---|---|
| 1 | Claude のメモリに「新規プロジェクト時は `gh api user` を最初に実行」を保存 | `~/.claude/projects/-Users-macmini-Desktop-Cursor/memory/feedback_new_project_preflight.md` | ✅ 実装済 |
| 2 | 共通リファレンスとして Pre-flight Check リストを作成 | 開発者個人の横断学習システム（外部リソース・本リポジトリ単独運用に支障なし） | ✅ 実装済 |
| 3 | 本プロジェクトに事故全プロセスを記録（このファイル） | `docs/learning-notes.md` | ✅ 実装済 |
| 4 | ユーザー側ルール: 新規プロジェクト時に「アカウント名確認した？」を最初に確認 | 記憶・習慣 | 運用中 |

### 横展開できそうなこと

- ローカル設定値（git config / npm config / aws config 等）と外部サービスのアカウント名は別物として扱う
- 「思い込み」より「実行コマンドでの検証」を優先する（特に固有名詞）
- 重要な固有名詞（URL / アカウント名 / リソース名）は記載前後に `grep -rn` で一貫性を確認する
- 残り 19 アプリの開発でも同様のチェックを適用すれば、同じ事故は防げる

### 教訓（カイゼン）

> 「動いた」「合ってそう」で進めず、**実コマンドで真偽を確定させる**。
> 推測で書いたコードや URL は、**書いた瞬間に grep / 実行で裏取り**する習慣をつける。

## 2026-05-08（追記）: PDCA・安心・安全システム自体の更新

### 何をしたか

事故後の振り返りで「**なぜ PDCA・安心・安全が機能しなかったか**」を分析。
真因として、両システムが**コード対象に設計**されており、**setup フェーズと事実検証**をカバーしていなかったことが判明。
システム自体を更新（標準化 = S の更新）した。

### 真因分析

| システム | 機能しなかった理由 |
|---|---|
| 安心・安全 3 ステップ | コードレビュー・ビルド・ヘルスチェックが setup フェーズ（コード無し）では適用不能 |
| 安心・安全 ステップ 1 | 「ハードコード値」は対象だが「事実として正しいか」は対象外 |
| PDCA の P | 受け入れ条件にサブタスク（固有名詞検証）を含めていなかった |
| 三現主義 | 「現場（GitHub）に行く」を実践せず推測で書いた |
| Jidoka | エラーシグナルが出ないドキュメント記載では発動できない |
| C（確認） | setup フェーズでは飛ばされてしまった |
| ブートストラップ | CLAUDE.md は自分自身の作成プロセスを守れない構造的問題 |

### 標準化（システム更新）

| 改善 | 場所 | 内容 |
|---|---|---|
| 1 | CLAUDE.md 17-1 ステップ1 | 「外部識別子の事実検証」を追加（gh api / aws describe / curl で裏取り） |
| 2 | CLAUDE.md 16-2 P 段階 | 「サブタスクごとに P を回す」追記。固有名詞は受け入れ条件に必ず含める |
| 3 | CLAUDE.md 17-4（新設） | Setup フェーズ用 3 ステップ（grep 検証・三現主義・Pre-flight 再走） + Setup 用 Jidoka 発動条件 |
| 4 | Pre-flight Check セクション 0（新設） | 自己診断質問 Q1-Q4 + Jidoka 発動条件（思考シグナルベース） |

### 横展開できそうなこと

- **「なぜ仕組みが効かなかったか」を仕組みのアップデートで応える**：個人の不注意のせいにしない
- 既存の安全策が**ある特定のフェーズでのみ機能**することを認識し、対応するチェックを増設する
- ブートストラップ問題（ルールがルール自体の作成を守れない）には、**外部リファレンス（Pre-flight Check）** で対応する
- 残り 19 アプリでは、これらの改善が事前に効くため、同種の事故は防げるはず

### 教訓（カイゼン）

> 仕組みが事故を防げなかった時、**個人を責めるのではなく仕組みを直す**。
> これがトヨタ式の本質であり、PDCAS の S（標準化）が指す対象は「個人の行動」ではなく「組織のシステム」である。

## 2026-05-08（追記2）: 横断学習システムの構築（PDCA on PDCA）

### 何をしたか

「事故を学習に変えるサイクル」を 6 段階（検知/分析/標準化/継承/検証/継続改善）で評価したところ、
**継承（20%）/ 検証（10%）/ 継続改善（0%）** が極めて低いことが判明。
1 プロジェクト内の単発サイクルは機能していたが、継続的なアプリ開発全体（規模を問わず）でのサイクルが閉じていなかった。
そこで横断学習システムを構築した。

### 真因

- Claude のメモリがプロジェクト（cwd）ごと独立しており、新プロジェクトに学びが自動引き継ぎされない
- 過去事故の一覧・教訓の抽象化・仕組みの定期見直しが、いずれも未整備だった
- 「継続すれば堅牢になる」という楽観論に依拠していたが、実際は同じ事故の再発リスクがあった（数を重ねれば自動的に良くなるわけではなく、症状発火型の見直しが必要）

### 標準化（システム構築）

| # | 場所 | 内容 |
|---|---|---|
| 1 | `_templates/incident-library/INDEX.md` | 全プロジェクト横断・事故ライブラリ |
| 2 | `_templates/incident-library/2026-05-08-github-account-confusion.md` | 今回事故の詳細記録 |
| 3 | `_templates/lessons-learned/INDEX.md` | 抽象化された教訓ライブラリ |
| 4 | `_templates/new-project-init-checklist.md` | Day 1 ルーチン（初日のやることチェックリスト） |
| 5 | `_templates/review-schedule.md` | 振り返りスケジュール（PDCA on PDCA） |
| 6 | `recipe-board/.github/pull_request_template.md` | 適用した仕組み・防げた事故ログを追加 |
| 7 | `recipe-board/CLAUDE.md` セクション 15 | 全プロジェクト横断・学習リソース参照 + 共通教訓 + 振り返りタイミング |
| 8 | メモリ `feedback_cross_project_learning_system.md` | 横断学習システムの利用ルール |

### 横展開できそうなこと

- 「事故を学習に変えるサイクル」を機能させるには、**個別プロジェクト内で完結させず、横断資産を蓄積する仕組み**が必要
- メモリ（プロジェクト独立）と外部ファイル（プロジェクト共有）の使い分けで補完する
- 「振り返りスケジュール」を予定として組み込まないと、サイクルは形骸化する
- 仕組みそのものへの PDCA（PDCA on PDCA）が、長期的な学習体制の鍵

### 教訓（カイゼン）

> サイクルは**閉じてこそサイクル**。
> 個別の事故対応で終わらせず、「複数プロジェクト横断の学習」「仕組み自体の見直し」まで繋げて、
> ようやく "事故を学習に変えるサイクル" は機能する。
